## 4. 第一群：明確な修正をU01→U05で進める

## 7. DB変更・移行のルール

既存migrationの編集・削除・squash・無断repairは禁止です。必要なDDLだけ新規append-only migrationにし、過去SQLの行数削減を目的にしないでください。

DB変更時は、旧アプリ/既存データとの互換、NULL/default/FK/unique/既存重複、RLS、関数owner/search_path/ACL、trigger副作用、index/lock/timeout、配備順と安全なforward-fix/rollback方針を確認します。生成型・inventoryは既存generatorで更新し、権限行列の期待値は設計した最小権限を根拠に変更してください。テストを緑にするためだけのgrant追加は禁止です。

空DB replayと、変更に関係する既存upgrade/deferred経路の両方を検証してください。CIの適用成功を配備先適用とみなさず、新通知migrationを含め対象環境の実履歴を確認します。配備操作は承認済み手順のみで、未適用を偽の成功fallbackで隠さないでください。

## 8. 各単位のテストと二段階レビュー

まず現行scriptsを確認し、存在するコマンドを使ってください。次は入力原本にある例で、実際の環境と既存規約に従います。

```bash
npm run lint:ci
npm run type-check
npm run type-check:commercial
npm run lint:commercial
npm run test -- --ci --testPathIgnorePatterns e2e red-contracts
npm run build
```

変更中はfocused回帰を先に回し、各PR完成時と依存変更の統合後に必要な既存ゲートを通します。上記の既存Jest除外範囲は広げないでください。認証/入力/権限にはsecurity回帰、UIにはApp E2E、middleware/CSPにはproduction-build Playwright、DB変更にはreplay/pgTAP/ACL/tenant/upgrade/生成型diffを加えます。通常8CIゲートとその検証内容を弱めないでください。

テスト期待値は承認仕様と独立に計算した正解から作り、実装と同じ誤りをコピーしないでください。mockでHTTP200を返すだけ、テスト用分岐、sample値、ゼロ/空配列の偽fallbackでGREENにしないでください。同梱の縮約probeが見つかっても本体テストの代用にはできません。

**レビュー1：要求適合。** 対象ID→現在の原因→変更→受入テストの対応、呼出元・通常/mobile/publicの契約、解消済み機能への退行を確認します。

**レビュー2：反例と障害。** 古い応答/並行更新/再試行/部分成功/後続ページ障害/tenant越境/権限剥奪/出力安全性/移行順序など、対象に関係する失敗条件を確認します。指摘を修正したら関係するテストを再実行してください。

独立した読取専用reviewerが実際に利用できる場合は、同一差分・同一SHAを渡し、実装とは分離して確認します。利用できなければ二段階の自己レビューと記録し、「独立2名監査済み」とは書かないでください。repo規約が独立レビューを必須にしている場合、代替した自己レビューでそのゲートをPASSにしないでください。

CIは確認対象のSHAとrun/job/stepを記録します。原本のrun `34009652063` は履歴で、新しい差分の成功証拠ではありません。過去のテスト件数を目標件数に固定せず、実際のpassed/failed/skipped/flakyを報告します。新規CIが未実行/参照不能ならCI未確認とし、ローカルPASSや過去CIで埋めないでください。

## 9. 中断・再開とスコープ制御

調査結果の提出後に、明確な修正の実施確認だけを求めて止まらないでください。U01から順に、許可範囲内で実装・検証を進めます。環境不足や仕様判断待ちがある場合、依存する単位だけBLOCKEDにし、独立して進められる単位へ移ります。

セッション上限等で継続できない場合は、最後に検証したSHA、現在の差分/未commit変更、完了したID、失敗/未実行テスト、次の具体的操作、必要な承認/設定名を台帳に記録してください。「残りも完了」「後で実行する」とは報告しないでください。次回は台帳とHEADを照合して未完了から再開し、完了項目を最初から監査し直さないでください。

今回の対象に直接関係しない新しい改善は別の保留欄へ記録し、作業を無制限に広げないでください。ただし安全性/データ破壊の明確な重大問題を発見した場合は無視せず、影響と根拠を報告し、必要な対象だけ停止します。

禁止：全面リライト、framework/ORM/認証/DB基盤の置換、microservices/Kubernetes/会社別DB、新queue製品、無測定の大量index、全依存major更新、`npm audit fix --force`、全UI/全hook刷新、100%coverage目的の作業、成功判定を得るためのgate/テスト/機能の削除。

## 10. 最終出力と完了条件

成果物はコード差分・回帰テスト・必要なmigration・更新台帳・次の最小作業です。計画書だけを成果物にしないでください。最終報告は日本語で、次を示してください。

```text
対象repo / 開始SHA / 最後に検証したSHA / branch / commit・PR:
読んだ2原本の実パス・文書ID・基準SHA:

IDごとの結果:
- 原本状態 / 現行再確認 / 今回の実行状態
- 原因、修正、変更ファイル/関数、影響するAPI・UI・DB契約
- REDのテスト名と原因 / GREEN・回帰のコマンド・環境・結果
- migration・追加設定・配備手順（秘密値は記載しない）
- レビュー1/2の対象と結果、独立レビューの実施有無
- 修正済みとして維持した範囲、未再現/条件付き/保留の理由
- 未実行・failed・skipped・flaky・BLOCKEDと解除に必要な具体条件

個別判定:
Code / Data correctness / Security / Capacity / Recovery /
Notifications / Production configuration / Operational readiness

次に必要な最小作業、対象ファイル、必要な承認/設定名:
```

「コード実装済み」「ローカル検証済み」「対象SHAのCI成功」「配備済み」「実環境受入済み」を別々に判定してください。未実施の容量・復元・通知・本番設定を含めて「10社100院運用可能」「製品出荷可能」と断定しないでください。

文書自身の最終merge SHAを埋めるためだけに、文書更新→merge→再更新を繰り返さないでください。固定した検証対象と、外部のcommit/checksへの参照で証跡を閉じます。

**まず2原本を読み、現行HEADと差分を確認して台帳を作成し、そのままPR-U01の本体回帰テストと最小修正に着手してください。現在HEADでU01が既に解消していれば証拠を記録し、次の未解消単位へ進んでください。**
