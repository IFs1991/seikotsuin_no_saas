## 1. 今回の製品範囲と前提

### 1.1 必須の提供範囲

- ログイン、ログアウト、招待受諾、スタッフ無効化。
- 独立会社間の分離、同一会社内の担当院・役職に応じた権限制御。
- 患者一覧・検索・登録・変更。
- 予約の一覧・作成・変更・キャンセル。
- 日報、売上・患者数の集計、本部・マネージャーの主要ダッシュボード。
- 契約済み会社への利用権限付与、契約状態に対応した書き込み制御。
- 最低限の障害検知、バックアップ復元、有人導入・利用停止・データ返却手順。

### 1.2 条件付きの提供範囲

メール・LINEの予約通知／リマインドは、提供する場合のみ `TASK-07` を出荷必須にする。AI、販促一斉配信、追加連携、追加ダッシュボードを今回まとめて完成させる必要はない。

**計画上の既定値は、主要業務を対象にする `core-100`。未検証の追加機能は提供対象外とする。** これは仕様・テスト計画上の既定値であり、既存本番機能を勝手に停止する指示ではない。現状の提供内容との相違は差分として報告する。

招待メール・パスワード再設定などの認証に必要な送信は、任意の予約通知機能とは区別する。予約通知を無効化するために、認証メールまで止めない。

### 1.3 変更しないもの

Next.js／Supabase／既存ホスティング／Redis／既存outbox／Sentryを基本的に維持する。料金、プランの含有院数、課金開始日、解約ルールは本仕様の変更対象外。100院の容量要件を、100院まで無償利用できる契約条件と混同しない。

会社は既存の `clinics.parent_id` 等による組織構造を利用する。100院は実店舗数であり、組織ルート用レコードは別に数える。組織ルートが10件必要なら、`clinics` が110行になる構成は正常である。新しい組織モデルへの移行はしない。

## 4. TASK-01：共有IPで正規ユーザーを締め出さない

### 対象ファイル

- `middleware.ts`
- `src/lib/rate-limiting/middleware.ts`
- `src/lib/rate-limiting/rate-limiter.ts`
- `src/app/(public)/login/actions.ts`
- `src/app/(public)/admin/actions.ts`
- `src/app/(public)/invite/actions.ts`
- 同じ認証処理を呼ぶ他の入口、既存の認証・レート制限テスト。

### 修正要件

1. `GET`／`HEAD`、ページ再表示、prefetch、静的ファイル取得を**ログイン試行の予算から除外**する。一般的なアクセス制限や認証判定は別物として維持する。
2. 実際の認証を実行するServer Action／Route Handlerの直前に、共通の認証試行ガードを適用する。パスのmiddleware修正だけで完了にしない。
3. 最小構成は「アカウント単位＋共有IP単位」の2段階とする。初期値は、アカウントの実認証試行10回／15分、IPの実認証試行100回／15分。既存の他の制限と重なって、実効上限が意図せず小さくならないこと。
4. この初期値では、成功・失敗を問わず実認証試行を数える。TTLで解除し、永久ロックは行わない。今回、失敗のみを数える複雑な二段階カウンタを新設する必要はない。設定値は中央管理し、結果を見て都合よく変更しない。
5. アカウントキーは、認証処理と同じ正規化をしたメールアドレス等から作る。生のメール・パスワード・トークンをRedisキー、ログ、Sentryに入れない。既存の安全なキー生成を優先し、不足する場合はサーバー側秘密を使うHMAC等を使用する。クライアントが申告した `user_id` を信用しない。
6. Redis側の判定・カウント・有効期限設定は、既存の原子的処理を再利用する。同時リクエストで全件が制限をすり抜けないこと。
7. `getClientIP` 等の既存実装を確認し、信頼できるプロキシ／ホスティング経由の値を使用する。任意の転送ヘッダーによる制限回避を前提にしない。
8. 招待受諾内のパスワード認証にも同じガードを使う。パスワード再設定メール送信は別の用途別制限を維持し、認証試行と無差別に同一カウンタへ混ぜない。
9. 本番でRedisが欠落・停止した場合の認証試行はfail-closed。APIでは503、Server Actionでは既存の型付きエラー契約に沿う。制限超過はAPIでは429と `Retry-After`、Server Actionでは同等の再試行待ち情報を安全に表示する。
10. Redis障害を通常のログイン失敗として数えない。運用通知を出すが、同一障害で大量通知しない。ブラウザ入力だけで解除できるバイパスを作らない。

上限は今回の実装初期値であり、全攻撃への耐性を証明する数値ではない。Supabase Auth側の独立したレート制限も確認し、アプリ側だけ変更して解決と判断しない。

### 受入テスト

- 同一IPの10アカウントが各3回ログインできる。計30回が旧3回制限で止まらない。
- 認証ページを20回表示しても、ログイン試行カウンタは増えない。
- 同一アカウントで10回試行後、11回目が制限され、TTL経過後に解除される。
- 複数IPから同一アカウントへ試行しても、アカウント側の予算は共有される。
- 同一IPでアカウント名を変えて大量試行すると、IP側制限が働く。
- 通常ログイン、管理者ログイン、招待経由のログインが共通ガードを通る。
- 同時試行、Redis障害、偽のユーザーID／転送ヘッダー、秘密情報の非露出を確認する。

9. データ取得失敗をゼロ件・ゼロ円へ置き換えない。失敗と本当のゼロを区別する。
10. migrationはappend-only。既存規約に従って仕様・ロールバックSQL・生成型・DBテストを揃える。測定や実行計画で必要性を確認したインデックスだけ追加する。

## 6. TASK-02B：予約一覧を最後まで取得できるようにする

### 対象ファイル

- `src/app/api/reservations/route.ts`
- `src/app/api/reservations/schema.ts`
- `src/lib/reservations/read-model.ts`
- 予約一覧APIを呼ぶ予約表、患者履歴、関連hook・service・DTO・テスト。

### API契約

- `id` 指定の単件取得は既存契約を維持する。
- 一覧取得に `limit` と `cursor` を追加する。初期値100、最大200。無効な値は400。
- 既存の `success` と `data` 配列を維持し、ページ情報を追加する。
- 下のレスポンスは**今回追加する契約例**であり、現状のレスポンスではない。

```json
{
  "success": true,
  "data": [],
  "pagination": {
    "has_more": false,
    "next_cursor": null
  }
}
```

既存の共通レスポンス型にページ情報の正式な置き場所がある場合は、それを再利用してよい。その場合は型・呼び出し元・テストを同時に更新し、採用した契約を報告する。

### 修正要件

1. 通常一覧は `(start_time ASC, id ASC)`、患者履歴は必要に応じて `(start_time DESC, id DESC)` など、ユニークなタイブレーカーを含む安定順序にする。
2. カーソルは並び順・検索条件と整合させる。不正・別条件のカーソルは400等の明示的エラーにする。カーソルは認可情報ではない。各ページで会社・院の認可を実行する。
3. `has_more` は上限＋1件取得等で正しく決める。本番のData API上限との関係を確認し、上限で切れた結果を「最後のページ」と誤認しない。
4. 予約表は表示期間に必要な全ページを取得する。月表示の最大6週を想定し、初期の表示期間上限は42日。既存により広い必要範囲がある場合は用途を確認して明示する。
5. 患者履歴はページ送りまたは追加読み込みにする。無期限の全履歴を一度にロードしない。
6. 一覧に期間・患者・IDのいずれもない無制限検索を許可しない。既存の呼び出し元を先に洗い出し、必要な条件を追加する。
7. APIだけ先に変更して、既存画面が最初の100件しか表示しない状態を作らない。利用箇所、型、キャッシュキー、テストを同一タスクで更新する。
8. 院・期間・検索条件を切り替えたら、旧リクエストを破棄または結果を無効化する。前の院のデータを混ぜない。
9. 途中ページが失敗した場合、予約表を全件取得済みに見せない。未完了表示と再試行を提供し、部分取得件数を合計値として使わない。
10. 固定データについて重複・欠落ゼロを保証する。並行編集で `start_time` が動く場合は再取得で整合させる。ページングを追加しただけで、同時更新中も完全なスナップショットを保証したと主張しない。
11. 現在の `start_date`／`end_date` の意味は利用箇所と照合する。JST境界を直す際も、既存利用者を黙って壊す変更をしない。

### 受入テスト

- 0／1／999／1,000／1,001／1,550件で全ページを取得し、期待ID集合と一致する。
- 同じ開始時刻の予約が複数あり、ページ境界をまたいでも欠落・重複しない。
- 昇順／降順、期間／患者／担当者フィルター、最終ページ、無効カーソルを確認する。
- JSTの23:59台／翌日00:00、月末月初、期間切替・院切替・途中通信失敗を確認する。
- A社のページから取得したカーソルをB社や担当外院に使っても、越境しない。

| `ENABLE_BILLING` | 有効 |

| `ENABLE_BILLING_TENANT_GUARD` | 有効 |
| `BILLING_ENABLED_PLANS` | 提供する既存プランを含み、空でない |
| `STRIPE_SECRET_KEY`／`STRIPE_WEBHOOK_SECRET` | 対象環境に存在し、test／liveを混同しない |
| `STRIPE_PRICE_GROUP_BASE_ID`／`STRIPE_PRICE_STORE_ADDON_ID` | groupを有効にする場合の既存設定 |
| `ENABLE_BILLING_OVERRIDES` | 利用する場合だけ期限・付与主体・監査ログを確認 |

### 修正・検証要件

1. 読み取り専用preflightで、必須設定の欠落・矛盾を列挙する。秘密値は出力せず、キー名・設定有無・対象環境・エラー分類だけを出す。
2. preflightは実際のアプリと同じ判定ロジックを再利用する。別スクリプトに条件を複製し、アプリと判定がずれる設計を避ける。
3. `NEXT_PUBLIC_*` はビルドされた値も確認対象にする。ローカルの環境ファイルが正しいだけで、デプロイ済み設定が正しいと判断しない。
4. 設定不備の503と、契約権限不足の402を分離する。画面でも運用設定不備を「お客様の未払い」と表示しない。
5. A社の契約が有効でも、B社に権限を与えない。院追加時の契約数量制御と並行処理を維持する。
6. Stripe test modeで有効化・支払失敗・解約・webhook再送／順序逆転を既存試験で確認する。実課金テストは人間承認がある場合だけ実施する。
7. 本番設定が既に正しければ、本体のガードを変更せず、preflight・テスト・証跡の追加で完了にしてよい。

### 受入テスト

- production相当／pilot OFF／設定正常／契約有効：主要業務の書き込み成功。
- 必須設定欠落：503相当になり、利用者の契約は変更されない。
- 未契約・利用停止：既存仕様どおり402等で拒否される。
- 猶予期間・解約予約・有効override・期限切れoverride：現行状態機械の期待値と一致。
- 他社の契約IDや院IDを指定：認可で拒否される。
- groupの院数上限付近で並行追加：過剰利用権限や誤った課金数量を作らない。

## 9. TASK-05：10社・100院の容量を実測する

### 9.1 検証データ

合成データのみ使用し、実患者のコピーを前提にしない。大きなseedを通常CIへ入れない。

| 項目 | 標準プロファイル |
| --- | --- |
| 独立会社 | 10社 |
| 実店舗 | 合計100院 |
| 院数分布A | 10院×10社 |
| 院数分布B | 50院＋6院×5社＋5院×4社＝100院 |
| スタッフ等 | 500アカウント。管理者・マネージャー・院スタッフを含む |
| 患者 | 標準10万件。導入時データが多い顧客を含める場合は30万件でも試験 |
| 予約 | 標準150万件（仮定：50件×100院×300営業日） |
| 日報・明細 | 予約・業務仕様に対応する件数。FKと集計整合性を保つ |
| 特殊ケース | 1,000件超の集計、同時刻の予約、月末、キャンセル、削除済み、未払会社、権限剥奪 |

データ件数は100院が空で存在するだけの試験を避けるための容量仮定であり、現在の実顧客数・実データ数ではない。

### 9.2 seedの安全要件

- 最初にdry-runし、対象URL／project ref／予定件数／実店舗と組織ルートの区別を表示する。秘密値は表示しない。
- 本番URL・本番projectへの投入を拒否する。明示許可された専用local／stagingだけを対象とする。
- 接続先は名前の文字列判定だけでなく、設定した許可対象と照合する。接続先が確定できなければ停止する。
- run IDに紐づくfixture一覧を残す。再実行で二重作成しない。
- cleanupは当該runの合成データだけを対象にする。共有DB全消去や全Authユーザー削除を行わない。削除自体も既存承認規約に従う。
- 大量データは適切なバッチで投入し、1行ごとの外部HTTP呼び出しにしない。RLS・制約・triggerを本番相当の検証時に無効化しない。
- seed時のservice_role利用と、負荷測定時の通常ユーザー利用を分離する。
- 既存規約上、local DBのresetやmigration適用にも承認が必要。未承認ならスクリプト作成・dry-runまでに留める。

### 9.3 負荷シナリオ

既存の負荷試験ツールがある場合は再利用する。ない場合はk6等の単一ツールまたは小さなランナーで足りる。負荷試験SaaSの契約は不要。WindowsローカルとLinux CIで使える入口にする。

| 工程 | 内容 |
| --- | --- |
| 動作確認 | 少数ユーザーで認証と業務シナリオが本当に成功するか確認 |
| ウォームアップ | 5分。測定区間とは別に保存する |
| 通常負荷 | 200アクティブユーザー、30分 |
| 短時間負荷 | 400アクティブユーザー、5分 |
| 回復確認 | 200ユーザーへ戻し、5分以内に通常基準へ復帰するか確認 |

初期の業務操作構成は、予約表閲覧45％、患者検索25％、予約作成・変更15％、日報5％、本部集計10％。役職に許可された操作だけを割り当てる。マネージャーへ予約作成権限を追加して試験を通さない。

1ユーザーあたり平均10秒程度の操作間隔を置き、実画面が1操作で複数APIを呼ぶ場合はそれも再現する。各ユーザー1シナリオずつ動かす。**VU数、操作／秒、HTTPリクエスト／秒、実DB負荷を分けて記録する。** 200VUを200RPSと同一視しない。

通常業務の測定で毎リクエスト新規ログインを繰り返さない。認証済みセッションを使い、ログイン集中試験は別に行う。一つの負荷生成機のIPに全100院を押し込んで、本番と違うIP制限を発生させた結果を容量不足と混同しない。逆に、通常負荷を通すために本番のレート制限を切ってはいけない。信頼できる試験構成で院ごとの共有IPを再現し、できない範囲は未検証とする。

### 9.4 合格条件

以下は**今回の初回受入基準**。実測値でも顧客向けSLAでもない。測定前に凍結し、失敗した後で合格に合わせて変更しない。

| 指標 | 通常負荷の基準 |
| --- | --- |
| 読み取りAPI | p95 ≤ 2秒 |
| 書き込みAPI | p95 ≤ 3秒 |
| 本部・マネージャー集計API | p95 ≤ 5秒 |
| 想定外エラー | 通常操作のリクエストで0.1％未満。5xx、timeout、意図しない429／4xx、200の業務失敗を含める |
| 会社・院の越境 | テスト上0件 |
| 確定済み予約の消失、禁止された重複、誤集計 | テスト上0件 |
| 短時間負荷後 | 接続枯渇・ロック・ジョブ滞留が残らず、5分以内に通常基準へ復帰 |

p95は主要エンドポイント／業務種別ごとに確認する。軽いAPIを大量に呼び、重い集計の遅さを全体平均で隠さない。p99、CPU、接続数、ロック待ち、DB容量、転送量、Redis操作数も測れる範囲で残すが、根拠のない細かい数値目標を大量追加しない。

400ユーザーの短時間負荷では通常時と同じレイテンシを必須にしない。ただし整合性・認可違反は認めず、負荷制御された拒否と原因不明のエラーを分ける。

競合を意図的に作るテストの409や、アクセス拒否テストの403は通常操作のエラー率とは分ける。通常の書き込みが全て402や429で失敗しているのに「高速」として合格にしない。

測定後に、既知の件数・売上・予約IDとDB状態を照合する。HTTP 200だけを成功条件にしない。

### 9.5 実行環境がない場合

ランナー・seed・負荷プロファイル・実行手順・結果記録の雛形まで作成し、実測を `BLOCKED` とする。本番同等のDBプラン、アプリプラン、リージョン、Data API上限、接続設定、レート制限構成、外部連携の状態が確認できないまま「100院対応済み」と報告しない。

データ分布AとBは同一の合成データの配置を変えて再検証できる形にする。小さなlocal試験は動作確認であり、100院の本番容量証明の代替ではない。

## 10. TASK-06：復元・監視・有人運用を閉じる

### 10.1 復元

既存のバックアップと復元手順を確認し、足りない部分だけ追記する。新しいバックアップ製品の開発はしない。

- 隔離環境へ復元し、患者・予約・日報・売上・会社境界・ログインを確認する。
- 使用中ならStorageの実ファイル、暗号鍵、Auth設定、外部連携設定も復旧対象に含める。DBバックアップだけで全て復元できると仮定しない。
- 復元先から本物のメール・LINE・Stripe webhook等を発生させない。Cron・外部送信を隔離した状態で確認する。
- 復元開始／完了時刻、利用可能な復元点、件数・集計・認可確認結果を記録する。
- RPO（失ってよい更新期間）とRTO（復旧までの時間）を本番提供条件に合わせて決める。初期推奨案はRPO 1時間以内・RTO 4時間以内。これは未承認の提案値なので、ownerの確定値を結果記録に入れる。
- 日次バックアップだけで1時間RPOを満たすと報告しない。必要な追加費用・仕組みは選択肢として報告し、無断で購入しない。
- 承認・復元先・バックアップが不足する場合は実施済みにせず `BLOCKED` とする。

共有DB全体の復元を、1社だけの誤操作の安易な対処に使わない。1社の修復が他9社の正常更新を巻き戻さない手順を明記する。専用の自動復元UIは不要。

### 10.2 監視

`src/lib/monitoring/sentry.ts` と既存計測を再利用する。

- テスト例外を発生させ、実際の通知先で受信を確認する。SDKがimportされているだけでは完了にしない。
- 認証／権限／契約設定の503、主要APIの継続的失敗、Cron失敗を検知する。
- 通知を提供する場合は最古の未処理outboxの待ち時間も検知する。
- 必要な画面のclient側とserver側について、DSN・初期化・ビルド反映を確認する。新しい監視基盤を並立させない。
- 患者名、メール、電話、予約メモ、Cookie、JWT、APIキー、通知本文をエラー情報へ流さない。
- 運用確認用エンドポイントは既存の管理権限・内部secret等で保護する。認証なしで設定やテナント一覧を公開しない。

### 10.3 導入・停止手順

短いrunbookを1本用意する。次が、有人対応で再現できればよい。

1. 会社ルート作成、実店舗追加、契約権限の確認。
2. スタッフ招待、役職・担当院設定、初期データ投入と件数照合。
3. テスト予約・日報・本部集計による受入確認。
4. スタッフ無効化、権限取消、会社の新規利用停止。
5. 障害時の新規展開停止、アプリの戻し方、DB変更がある場合のforward-fix判断。
6. 会社単位のデータ返却／削除の承認付き手順。削除は保持義務・契約条件の確認なしに実行しない。
7. 各社に窓口を1つ設け、100院すべてからの個別対応を前提にしない。

必要な利用契約・データ取扱いの整備状況はowner確認事項とする。Codexに法令適合の認定や不要な法務文書の大量生成をさせない。

### 10.4 リリース設定

ブランチ保護・required checks・本番デプロイの経路を読み取り確認する。未設定なら変更案を記録し、管理設定の変更はowner承認後に行う。ソロ開発に不要な組織承認フローを新設しない一方、既存規約のレビュー要件を勝手に省略しない。

8. 外部送信が成功した直後にworkerが落ちるケースを扱う。providerの冪等キーや照合手段を使う。結果不明なのに無条件で再送しない。照合できない場合は要確認として可視化し、手動確認経路を残す。
9. 「exactly onceを保証」といった証明できない説明はしない。今回の故障注入テストで重複がないことと、保証範囲を分ける。
10. 提供しない場合はUIだけでなくAPI・enqueue・Cronの実行経路も止まることを確認する。ただし未送信outboxを無断削除せず、既存顧客への提供停止も無断で行わない。

## 12. 新設スクリプト・文書の最小セット

以下は候補名。**現在存在するコマンドではないものを含む。** 同等の既存スクリプトがある場合は拡張し、実際の実行コマンドを成果物へ記載する。

```powershell
npm run build
```

これだけでは全CI・DB・E2E・負荷試験は網羅しない。実装後に `package.json` と最新CIを照合し、必要な追加コマンド、前提条件、実行した環境を結果記録へ残す。buildには必要な非本番設定を用意し、実キーを貼り付けたコマンド例を作らない。

DBやfixtureを変更するコマンドは、間接的な呼び出しも含めて実行内容と対象を確認し、既存承認規約を満たしてから実施する。

## 13. 既存の商用基準・過去FAILとの整合

既存の `docs/releases/commercial-release-qualification-v1.0.md` は一般商用提供の厳しいゲートを持つ。本仕様は10社100院の実用上必要な修正と受入条件を定めるが、既存規約・本番承認条件を黙って上書きしない。

- 過去のPR-11で記録された一括登録ベンチマークのFAILは、そのまま保持する。
- 新しい `core-100` の製品SLOを、過去の固定ベンチマークとは別の結果として記録する。
- 本仕様の目的に直接関係しない数十msの最適化を、Codexが自発的に作業へ追加しない。
- 既存文書が過去ベンチマークを商用必須条件としている場合は、**適用範囲を整理する差分案**を作る。owner承認なしにそのゲートを削除・免除したり、リリースGOを宣言したりしない。
- 旧文書の未更新ステータスと、最新コード・最新検証結果を区別する。古い `NOT_RUN` だけから、今の機能が未実装と断定しない。
- セキュリティ、会社分離、データ整合性、復元の要件は縮小の対象外。

新たな多層承認プロセスは不要。必要な既存ゲートとの差分を1か所へ集約し、未承認項目だけを明示する。

## 14. 完了判定と結果記録

### 14.1 状態の区別

- `IMPLEMENTED`：コード・テストを追加／修正した。実行合格とは別。
- `PASS`：対象コミット・対象環境・条件で実行し、合格した。
- `FAIL`：実行して不合格。
- `NOT_RUN`：未実行。
- `BLOCKED`：環境・権限・承認などの不足で実行できない。
- `NOT_APPLICABLE`：提供範囲外で、呼び出し不能・ジョブ停止等の根拠がある。

同等の既存機能で満たす場合は、不要なコード差分を作らず、既存実装のパスとPASS証跡を記録する。

### 14.3 出荷チェックリスト

- [ ] 同一院の共有IPで通常ログイン・再ログイン・招待受諾ができる。
- [ ] 実際の認証入口で不正な連続試行を制限できる。
- [ ] 1,000件を超える集計・予約一覧に欠落・誤集計がない。
- [ ] pilot OFFで契約済み会社が主要業務を書き込める。
- [ ] 別会社・担当外院・無効化後のアクセスを拒否する。
- [ ] 出荷対象コミットのCI・DB・主要業務E2Eが合格している。
- [ ] 100院相当データと通常／短時間負荷を実測し、基準を満たしている。
- [ ] バックアップ復元と復元後の会社分離を確認している。
- [ ] 障害通知が実際に担当者へ届く。
- [ ] 本番設定、契約権限、導入・停止・復旧の担当と手順が確定している。
- [ ] 通知を提供する場合はTASK-07合格。提供しない場合は非公開の根拠がある。
- [ ] 既存商用ゲートとの適用差分、本番変更・出荷承認が解決している。

コードだけ完了し、容量・復元・本番設定が未確認なら、報告は**「修正完了／出荷未判定」**とする。ローカルPASSだけで「10社100院の製品版完成」としない。

## 15. Codexの最終報告形式

以下を短くまとめる。報告の長さではなく、差分と検証結果を重視する。

1. 修正したタスクIDと、主な変更ファイル・関数。
2. 既存実装で充足し、変更しなかった項目。
3. 実行したコマンド・対象コミット・環境・成功／失敗。
4. 未実行・BLOCKED項目と、解消に必要な具体的条件。
5. migration、追加環境変数、設定変更の有無。秘密値は出さない。
6. API契約の変更と、追従させた呼び出し元。
7. リリース判断：コード／容量／運用を別々に示す。
8. 残リスクと、次に必要な最小作業。

**今回作らないもの：** マイクロサービス、Kubernetes、会社別DB、マルチリージョン、汎用権限基盤の再設計、100％テストカバレッジ、全面UI刷新、完全セルフオンボーディング、新課金エンジン、汎用配信基盤。

測定で不足が判明した場所だけ追加で修正する。必要十分な製品化で止める。
