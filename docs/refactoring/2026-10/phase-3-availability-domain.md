# Phase 3 — 業務ルールを分けたまま判定を整理する

v1.1 / tracker #138。これは統一エンジンの実装指示ではない。共通化案を採用しない判断も許す。開始条件は対象consumerの[P1契約](phase-1-contracts.md)と本人ID対応の確認。

## 1. 同じ「空き」でも意味が違う

| consumer | 維持すべき固有条件 |
| --- | --- |
| 院内予約・タイムライン | 現場の手動登録/例外、表示と編集の権限、既存UI契約 |
| 公開予約 | 営業時間、受付期間、メニュー所要時間、公開・認証条件 |
| ロスター候補 | 勤務希望、既存配置、他院ヘルプの条件。予約の空き検索とは別 |
| 新しい他院照会 | 指定院・指定区間に予定上対応可能か。予約確定や移動可能性を保証しない |

共通化の第一候補は区間重複・status分類・日時変換等の既存helperの再利用。UI、認可、DB読取、業務方針、最終書込制約を一つの巨大サービスに詰め込まない。新しいAPI・RPC・テーブル・汎用repositoryを先に作らない。

## 2. 実装前に決める論点

- `staff_id`と院別`resource_id`、任意の`staff_profile_id`、所属院・実勤務院の対応を確認する。全行にprofileが存在すると仮定せず、表示名による名寄せはしない。
- confirmed勤務の扱い、シフト未登録/読取失敗、休憩・blocksの表現をconsumer別に決める。新しい必須条件の導入はFIXまたはFEATUREへ分離する。
- 時間は原則半開区間`[start,end)`で提案し、現行契約との一致を確認する。日跨ぎ・前日開始の予約/blocks・勤務境界を取りこぼさない。
- 資格、対応メニュー、準備時間、同時対応数は現仕様を確認する。院ごとのmenu IDの単純比較、max_concurrentを根拠にした排他制約緩和はしない。
- 決定記録は当該PR内に`論点 / 現挙動 / 選択肢 / 採用理由 / 承認者 / 影響consumer`の小表で残す。必要もないADRファイルは増やさない。

## 3. 最小のPR分割

A. consumer差分と本人ID対応を調査・決定する（docs/test）。
B. 同値性を示せる純粋な重複処理だけ抽出し、最初の既存consumerへ接続する（refactor）。
C. 2つ目以降のconsumerを1つずつ移行し、固有policyを保持する（個別refactor）。
D. 利用者が移行済みの旧処理だけ撤去する（cleanup）。

既存挙動と期待仕様が違うなら、修正は別FIX PRでRED→GREEN。REFACTORのgreen→greenと混ぜない。消費者のない新共通層だけを先にmergeしない。

## 4. 他院照会で再利用する場合の安全条件

scopeはサーバー側の検証済みcontextから決定する。membershipやprofile検索で院集合を拡張しない。service-roleでも無制限な全院検索をしない。範囲外の予約詳細を取ってからUIで隠す設計は禁止。

新しい照会では`available / unavailable / unknown`を区別する。必須データ欠落・一部取得失敗・本人対応不明を「空き0件」または「空いている」に変換しない。scope外は情報付きunknownではなく拒否する。判定の完全性を確認できない場合、全店舗での空きを保証しない。

出力は許可院・必要なスタッフ表示情報・対象区間・判定時刻に限定する。患者名、予約内容、電話、住所、内部profile IDは不要なら返さない。許可内の情報であっても理由欄へ予約詳細を入れない。

## 5. 受入例（採用policyを併記）

| ケース | 検証すること |
| --- | --- |
| 11–12時予約の直後12時開始／11:30開始 | 採用した境界規則と途中重複 |
| 17時勤務終了、16:45開始30分 | 新しい勤務判定では区間全体を満たさない |
| 休憩/active block、取消/削除 | 有効区間とstatusのpolicy差 |
| シフト不明／API失敗／ID対応不明 | 新照会でunknown。旧登録契約を黙って変更しない |
| 同じ人が異なる院別resourceを持つ | 誤名寄せ・二重表示・誤った勤務院判定を防ぐ |
| 日跨ぎ、境界直前の既存予定 | start時刻の日付フィルタだけで除外しない |
| 他組織、権限剥奪、scope縮小 | データ/件数/キャッシュから漏洩しない |
| 照会直後に他者が予約 | 書込時の既存DB排他と再検証を維持 |

新照会は[P5の独立FEATURE判断](phase-5-ui-and-feature-gate.md)へ渡す。公開予約の新ルール導入や別院への応援自動化は、このPhaseの完了条件に含めない。
