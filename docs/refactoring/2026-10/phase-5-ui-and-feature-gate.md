# Phase 5 — UIの責務整理と新機能の独立判断

v1.1 / tracker #140。UIリファクタリングは当該[P1契約](phase-1-contracts.md)があれば着手可能。OS全体やP2/P4の完了を待たない。

## UIリファクタリング

予約画面の状態・取得・イベント・モーダルのうち、変更時の責務が混ざる箇所だけ分離する。行数基準による機械的な細分化はしない。JSXを別ファイルへ移すだけで依存が増えるなら採用しない。

現行の表示、導線、クリック/ドラッグ/キーボード操作、日付/院切替、read-only権限、loading/error/empty/retryを固定して比較する。Design.mdのEXTENDに従い、テーマや共有componentの全体変更を混ぜない。

空通知UIや操作の削除は利用実態と業務承認が必要であり、見た目が変わらないrefactorではない。UI権限とサーバー認可を分離し、参照機能を追加するために編集権限を緩めない。

## 別FEATURE: 他院の同時刻空きスタッフ照会

本Programでは着手可否と必要条件を整理するだけ。実装は別Issue/PR。必要な[P3契約](phase-3-availability-domain.md)が揃えば、無関係なリファクタリング完了は待たない。

最小UX案: 時刻選択 → 「他院の空き状況を参照」→ 許可院・スタッフ・連続空き区間・判定時刻を表示。閲覧専用ユーザーでも、必要な参照権限がある場合だけ起動できる。

指定開始時刻だけでなく施術所要時間全体を判定する。勤務先、休憩/blocks、取消status、本人ID対応、必要な資格/メニュー互換性の未確定事項を残したまま「予約可能」と表示しない。unknownと取得失敗のUI、再照会、競合時の案内を定義する。

患者情報の返却・別院の予約書込・スタッフ配置変更・応援自動化は非対象。scopeの自動拡張はしない。移動可能性は別問題として表示を分ける。

## GO / DEFER

初期の検証案は2〜3院の受付業務で、他院照会の実頻度、現在の電話/画面切替工数、紹介成立、誤案内リスクを記録すること。件数や売上改善は仮説と実測を分ける。実店舗試験は個別承認が必要。

GOは利用者・課題・最小仕様・データ完全性・権限・回帰テスト・運用責任者が明確でWorksの優先業務を圧迫しない場合。そうでなければDEFER理由をIssueに残す。新機能を作らない判断でも、本フェーズの判断作業は完了できる。
